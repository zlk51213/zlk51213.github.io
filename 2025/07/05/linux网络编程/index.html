linux网络编程

网络分层

OSI七层模型

  • 物理层：实现实际终端信号的传输，码流通过物理介质传输，常用设备：集线器，中继器，网线，双绞线 主要协议：IEEE802.3
  • 数据链路层：提供介质访问和链路管理。把位元合并为字节，然后将字节合并到帧中，使媒体能够通过数据链路层访问，常用设备：交换机，网卡，网桥，主要协议：ARP，RARP，STP，FDDI，PPP，HDLC，VLAN
  • 网络层：IP地址及路由选择，通过IP选择了解两个端的连接。为源端传输送来分组。选组合适的路由和交换节点，按照地址，准确的地送到目的端的传输 层，常用设备：路由器，主要协议：IP，ICMP，IGMP，ARP，RARP，OSPF，IPX，RIP，BGP
  • 传输层：建立，维护，管理端到端的连接，为端到端的数据传输提供可靠传输。常用设备：网关，主要协议：TCP，UDP，SPX
  • 会话层：建立，管理，维护表示层实体的会话，常用设备：网关，主要协议：RPC，SQL，NFS，NETBIOS，ASP，ISO 8327 / 8347
  • 表示层：数据格式转换，加密，解密，压缩，解压缩，常用设备：防火墙，主要协议：JPEG，MPEG，ASII，TIFF，GIF，PIF，DES，MPPC
  • 应用层：为应用程序提供服务，如HTTP，FTP，DNS，SMTP等，常用设备：防火墙，主要协议：HTTP，HTTPS，FTP，POP3，SMTP，DNS，DHCP，Telnet，SNMP，RTSP，SIP，SSH，NFS，CIFS，SOAP，Gopher

TCP/IP四层模型

  • 网络接口层：对应OSI模型的物理层和数据链路层，负责将数据帧从发送端传输到接收端，常用设备：网卡，网桥，交换机，主要协议：ARP，RARP，IEEE 802.3
  • 网际层：对应OSI模型的网络层，负责将数据包从源主机传输到目标主机，常用协议：IP，ICMP，IGMP，ARP，RARP，OSPF，IPX，RIP，BGP
  • 传输层：对应OSI模型的传输层，负责在源主机和目标主机之间建立端到端的连接，常用协议：TCP，UDP，SPX
  • 应用层：对应OSI模型的会话层、表示层和应用层，负责为应用程序提供网络服务，常用协议：HTTP，FTP，DNS，SMTP等

UDP

  • UDP是无连接的，发送数据之前不需要建立连接，因此减少了开销和延迟

  • UDP是面向报文的，对应用层交下来的报文，不合并，不拆分，只是添加UDP头后交给网络层

  • UDP没有拥塞控制，因此网络出现拥塞不会使源主机的发送速率降低（对实时应用很有用，如IP电话，实时视频会议等）

  • UDP支持一对一，一对多，多对一和多对多的交互通信

  • UDP的首部开销小，只有8个字节，比TCP的20个字节的首部要短
    UDP适用情况

      发送小尺寸数据（如对DNS服务器进行IP地址查询时）
  在接收到数据，给出应答较困难的网络中使用UDP。（如：无线网络）

广播、组播模式
即时通讯软件的点对点文本通讯以及音视频通讯
流媒体、VOD、VoIP、IPTV等网络多媒体服务中的实时数据传输

UDP通信流程

发送方：
创建 UDP 套接字： int fd = socket();
准备好接收方的地址：struct sockaddr_in peerAddr;
给对方发送 UDP 数据报：sendto(fd, peerAddr);
接收方：
创建 UDP 套接字：int fd = socket();
准备好自己的地址：struct sockaddr_in addr;
绑定套接字和地址：bind(fd, addr);
坐等各方发来的 UDP 数据报：recvfrom(fd);

TCP

传输控制协议(TCP)是Ineternet协议套件中的传输层协议，它提供了可靠，有序，面向连接的字节流服务。应用程序在使用TCP之前，必须先建立TCP链接；TCP通过校验和，序列号，确认应答，重发控制，连接管理，窗口控制等机制实现可靠传输；在发送数据之前，TCP协议会将数据划分成报文段，为每个报文段分配序列号，并确保接收端对收到的数据进行排序，最终将有序报文段重新组合成数据流。

TCP基本特征

有连接：通信双方需要事先连接成功，方可传输数据
有确认：一方收到对端的任何数据，都会给另一方发回执确认
保证数据有序、不重复、丢失会重发
如果网络拥堵，会自动调节发送量
采用帧异步的流式通信方式（即通信双方每次的收发数据量不必相等）

TCP适合用情形：

传输质量要求较高，不能丢失数据
大数据量的通信，以至于通信前后的连接和断开的开销可以忽略不计
用户登录、账户管理等相关的功能

TCP三次握手

TCP三次握手的过程如下：
第一次握手：客户端向服务端发送一个TCP报文段，该报文段中包含SYN标志位，表示请求建立连接。同时，客户端会随机生成一个初始序列号seq。
第二次握手：服务端收到客户端的SYN报文段后，会向客户端发送一个TCP报文段，该报文段中包含SYN和ACK标志位，表示同意建立连接。同时，服务端会随机生成一个初始序列号seq，并将客户端的序列号+1作为ACK号。
第三次握手：客户端收到服务端的SYN+ACK报文段后，会向服务端发送一个TCP报文段，该报文段中包含ACK标志位，表示确认连接建立。同时，客户端会将服务端的序列号+1作为ACK号。
握手过程中第一次和第二次传送的包里不包含数据，第三次握手可以携带数据

TCP如何保证可靠传输

TCP通过以下机制来保证可靠传输：
数据校验：TCP报文段中包含校验和字段，用于检测数据在传输过程中是否发生错误。
序列号：TCP报文段中包含序列号字段，用于标识每个报文段的顺序。接收方可以根据序列号字段重新组装报文段，并检测是否有报文段丢失或重复。
确认机制：接收方在接收到TCP报文段后，会向发送方发送一个确认报文段，表示已成功接收到数据。发送方会根据确认报文段中的确认号来调整发送窗口的大小，确保数据的有序传输。
超时重传：如果发送方在一段时间内没有收到确认报文段，则会重新发送未确认的数据报文段。
流量控制：TCP使用滑动窗口机制来实现流量控制，避免发送方发送的数据量超过接收方的处理能力。
拥塞控制：TCP使用拥塞控制算法（如拥塞避免算法）来控制网络的拥塞程度，避免网络拥塞导致的数据丢失和传输延迟。

如何解决粘包问题

粘包问题是指TCP协议在传输数据时，将多个数据包合并成一个数据包进行传输，导致接收方无法区分每个数据包的边界。解决粘包问题的方法有以下几种：
1.定长发送：发送方将每个数据包设置为固定长度，接收方根据固定长度来接收数据包。这种方法简单易行，但需要发送方和接收方协商好数据包的长度。
2.尾部标记序列：发送方在每个数据包的尾部添加一个标记序列，用于标识数据包的结束。接收方根据标记序列来区分数据包的边界。这种方法需要发送方和接收方协商好标记序列。
3.头部标记分步接收(最实用)：定义一个用户报头，在报头注明每次发送的数据包大小，接收方每次接收时先以报头的大小进行数据读取，这必然只能读取到一个报头的数据，从报头中获得该数据包的大小，再根据这个大小去读取数据包，这样就能保证每次读取一个完整的数据包。这样一来，每个数据包发送时都封装一个报头，接收方每次接收时都先接收报头，再根据报头中的数据包大小去接收数据包，这样就能保证每次接收一个完整的数据包，从而解决粘包问题。

TCP建立连接之后怎么保持长连接

有两种技术可以运用，一种是有 TCP 协议层实现的 Keepalive 机制，另一种是由应用层自己实现的 HeartBeat 心跳包。

  • 1在 TCP 中有一个 Keep - alive 的机制可以检测死连接，原理很简单，当连接闲置一定的时间（参数值可以设置，默认是 2 个小时）之后，TCP 协议会向对方发一个 keepalive 探针包（包内没有数据），对方在收到包以后，如果连接一切正常，则应当回复一个 ACK；如果连接出现错误了（例如对方重启了，连接状态丢失），则应当回复一个 RST；如果对方没有回复，那么，服务器每隔一定的时间（参数值可以设置）再发送 keepalive 探针包，如果连续多个包（参数值可以设置）都被无视了，说明连接被断开了。

  • 2 心跳包之所以叫心跳包是因为：它像心跳一样每隔固定时间发一次，以此来告诉服务器，这个客户端还活着。事实上这是为了保持长连接，至于这个包的内容，是没有什么特别规定的，不过一般都是很小的包，或者只包含包头的一个空包。由应用程序自己发送心跳包来检测连接的健康性。客户端可以在一个 Timer 中或低级别的线程中定时向服务器发送一个短小精悍的包，并等待服务器的回应。客户端程序在一定时间内没有收到服务器回应即认为连接不可用，同样，服务器在一定时间内没有收到客户端的心跳包则认为客户端已经掉线。

TCP和UDP的区别

TCP和UDP是两种不同的传输协议，各有优缺点，选择使用哪种协议取决于具体的应用场景和需求。它们之间的主要区别如下：

  • 连接性：TCP是面向连接的协议，而UDP是无连接的协议。TCP需要建立连接、确认连接和断开连接，而UDP不需要。这意味着在使用TCP传输数据时，发送方和接收方需要在发送数据前先建立连接，而在使用UDP传输数据时，发送方可以立即将数据传输到接收方。

  • 可靠性：TCP是可靠的协议，而UDP是不可靠的协议。TCP使用确认机制、超时重传机制和数据校验等方式来保证数据的可靠性，而UDP没有这些机制。这意味着在使用TCP传输数据时，如果数据包丢失或出错，发送方会重传数据包，直到接收方成功接收到数据为止。而在使用UDP传输数据时，如果数据包丢失或出错，发送方不会等待接收方的回应，也不会重传数据包，直接将数据发送出去。

  • 速度：UDP比TCP快。由于TCP需要建立连接、确认连接和断开连接等过程，所以在传输数据时会有一定的延迟。而UDP没有这些过程，所以传输速度相对较快。

  • 报文格式：TCP和UDP的报文格式不同。TCP将应用层传递下来的数据看作是无结构的数据流，并在传输层添加了序号、确认机制、超时重传机制和数据校验等机制。而UDP在IP协议的基础上添加了端口和差错检查的功能，没有对数据进行序号、确认和重传等处理。

  • 应用场景：TCP适用于对数据传输可靠性要求较高的场景，如文件传输、邮件发送等。而UDP适用于对速度要求较高但对数据可靠性要求较低的场景，如视频流传输、游戏等。

TCP四次挥手

TCP连接的关闭是通过四次挥手来实现的。具体过程如下：

  • 第一次挥手：当客户端想要关闭连接时，它会发送一个FIN（Finish）标志位为1的数据包给服务器，表示客户端已经没有数据要发送了，但是客户端仍然可以接收服务器发送的数据。
  • 第二次挥手：服务器收到客户端的FIN数据包后，会发送一个ACK（Acknowledge）标志位为1的数据包给客户端，表示服务器已经收到客户端的关闭请求。
  • 第三次挥手：当服务器没有数据要发送给客户端时，它会发送一个FIN标志位为1的数据包给客户端，表示服务器已经没有数据要发送了，但是服务器仍然可以接收客户端发送的数据。
  • 第四次挥手：客户端收到服务器的FIN数据包后，会发送一个ACK标志位为1的数据包给服务器，表示客户端已经收到服务器的关闭请求。此时，TCP连接关闭。

TCP四次挥手中的TIME_WAIT状态是为了确保对方收到最后的ACK报文，防止连接的延迟报文段。客户端进入TIME-WAIT状态后，需要等待2MSL时间，以确保服务器收到自己的ACK应答报文。服务端不需要等待这段时间。挥手需要四次是为了保证连接的可靠关闭。

connect卡顿优化

由于数据包在网络中的传输是需要时间的，并且会因为网络拥塞的原因导致接收延时，因此三次握手并非一瞬间就能完成，比如客户端很有可能由于网络不畅导致迟迟不能得到服务端的确认，那么有时为了更好的用户体验和必要的逻辑控制，一般要给 connect() 套接字加上连接进度和超时控制，以便于在无法连接或者缓慢连接服务器的场景下，提供更好的使用体验。

TCP数据缓冲区

在 TCP 通信当中，发送方和接收方都有所谓的缓冲区，发送方的缓冲区用来为数据的丢失重发做准备，接收方的缓冲区配合水位线可以用来规范接收数据块的大小。

发送缓冲区

在Linux下，TCP的发送缓冲区大小一般介于 4608-425984 之间，不同主机的检测结果可能有所不同。发送缓冲区的基本作用，是当接收方发现数据丢失要求发送方重发时，发送方有备份数据可以重新发送。注意，这里提到的发现数据丢失、要求重发等行为，是TCP协议本身的自动机制，不需要应用层软件参与。

接收缓冲区

在Linux下，TCP的接收缓冲区大小一般介于 2304-425984 之间，不同主机的检测结果可能有所不同。接收缓冲区的最初概念，是套接字从网络接收到的数据在暂存区，尤其当传输的数据是结构化数据时，设定特定大小的缓冲区就特别有用，比如收发大小为100个字节的结构体，那么为了保证接收方每次收到的都是完整的100个字节的整块数据，可以将接收缓冲区设定为100。

水位线

水位线是个很形象的说法，TCP将接收缓冲区视为一个水池，原则上只有等水池的水满了（接收的数据填满了缓冲区），应用层才能读取到数据，但为了更灵活，TCP增加了一个叫水位线的概念，规定：当接收数据量超过水位线时，就触发套接字的 读就绪 状态，使得应用层的 read() 函数可以正常读取数据。

OOB带外数据

虑这样一种情形：接收方设置了较大的缓冲区（比如10000字节）和较高的水位线（比如100字节），由于接收的数据量必须要达到水位线（默认是1字节）才能使套接字读就绪，因此在接收较少数据（比如80个字节）时，发送方发出的数据就会滞留在接收方的缓冲区中，若此时恰好有一些比较紧急的数据（比如一些控制信息），那这些数据就会被被迫滞留在缓冲区中无法被接收方读取，造成逻辑上的缺憾。

解决这个问题的办法是：将紧急数据设定为 带外数据，通过特殊的标志位，让其抵达接收方后可以冲破缓冲区和水位线的限制，让接收方可以优先读取。这种机制就是 TCP 的 OOB（Out of Band） 数据。

OOB的基本性质

            OOB 数据指的是在 TCP 通信中的一种特殊数据，它能冲破接收端缓冲区和水位线的限制。
            OOB 数据的到达会触发对端套接字产生 SIGURG 信号。
            OOB 数据的到达会使得对端套接字处于异常就绪状态，可以通过 select 监测到。
            OOB 数据每次只能发送 1 个字节，但是可以发送多次。
            OOB 数据只能使用 recv() 和 send() 来收发。

IO模型

所谓服务器IO模型，指的是当一个服务端网络程序需要同时处理多个套接字时，采取什么策略去妥善处理它们。由于网络数据的到达是无法预见的，因此不能像读取本地数据那样直接读取，要考虑如果数据不能及时到达应该如何处理的问题。

一般而言，服务端IO模型包括：

  • 非阻塞轮询
  • 多任务并发
  • 异步信号
  • 多路复用

非阻塞轮询

非阻塞轮询是最简单的IO模型，它通过设置套接字为非阻塞模式，然后不断轮询套接字的状态，如果套接字有数据可读，则读取数据，否则继续轮询。这种模型虽然简单，但是效率低下，因为每次轮询都需要消耗CPU资源，而且如果多个套接字同时有数据可读，那么需要逐个处理，无法同时处理多个套接字。

多任务并发

多任务并发是另一种IO模型，它通过创建多个线程或进程，每个线程或进程处理一个套接字。当某个套接字有数据可读时，对应的线程或进程会读取数据，然后处理数据。这种模型可以同时处理多个套接字，但是每个线程或进程都需要消耗系统资源，而且如果多个线程或进程同时有数据可读，那么需要逐个处理，无法同时处理多个套接字。

设计思路

对于UDP而言，由于不存在连接的问题，因此服务端一个UDP套接字可以接收任意的客户端发来的数据，可直接将该套接字交由一条专用于收发数据的线程管理即可。

对于TCP而言，稍微复杂一点，首先需要一条专门的线程处理监听套接字，用来随时接受客户端的连接请求。另外由于每当有一个客户端连接成功，服务端都会产生一个新的连接套接字来与之通信，那么就应该每产生一个套接字就分配一条线程与之对应，便可形成所谓的 多任务并发 的服务器IO模型。

注意点

总体而言，多线程处理服务端IO模型是比较简单的，注意几点：
UDP没有连接，因此多线程模式一般用于TCP服务端
每个线程处理一个已连接套接字
线程一般要处于分离状态，避免产生僵尸

异步信号

异步信号是另一种IO模型，它通过设置套接字的信号处理函数，当套接字有数据可读时，会触发信号处理函数，然后处理数据。这种模型可以同时处理多个套接字，而且每个套接字的数据到达时，只会触发对应的信号处理函数，不会影响其他套接字的处理。但是，异步信号模型需要使用select、poll、epoll等函数来监听套接字的状态，因此需要额外的系统资源。

适用场景

首先明确一点，由系统套接字触发的是第29号信号：SIGIO
由于不管套接字收到何种数据，内核一律触发 SIGIO，因此这种看似很理想的方式，却不适用于 TCP 协议，因此在 TCP 中，当客户端发来连接请求、普通数据、数据回执，甚至是断开请求、断开请求的回执等等情况，都触发一样的信号，这就使得服务端光凭这一个信号无法知道下一步要做什么，因此信号驱动的服务器模型，一般只适用于UDP协议。

说明：
信号 SIGIO 默认会杀死目标进程，因此必须要设定其响应函数；信号SIGIO由内核针对套接字产生，而内核套接字可以在多个应用层程序中有效（例如父进程将套接字遗传给各个子进程），因此必须指定该信号的属主；默认情况下，套接字收到数据时不会触发 SIGIO，必须将套接字设定为异步工作模式，它才会触发该信号。

多路复用

多路复用是另一种IO模型，它通过使用select、poll、epoll等函数来监听多个套接字的状态，当某个套接字有数据可读时，会触发对应的回调函数，然后处理数据。这种模型可以同时处理多个套接字，而且每个套接字的数据到达时，只会触发对应的回调函数，不会影响其他套接字的处理。而且，多路复用模型只需要一个线程或进程就可以处理多个套接字，因此可以节省系统资源。

多路复用接口

select

原理：select函数通过一个文件描述符集合来监听多个套接字的状态，当某个套接字有数据可读时，select函数会返回，并将对应的文件描述符添加到另一个集合中，然后程序可以通过遍历这个集合来处理数据。

int select(int nfds,fd_set *readfds,fd_set *writefds,fd_set *exceptfds,struct timeval *timeout);
参数：

  • nfds：监听的文件描述符数量，通常为最大的文件描述符加1。
  • readfds：需要监听的读事件文件描述符集合。
  • writefds：需要监听的写事件文件描述符集合。
  • exceptfds：需要监听的异常事件文件描述符集合。
  • timeout：超时时间，如果为NULL，则表示一直等待，直到有事件发生。

返回值：

  • 成功时返回就绪的文件描述符数量，如果超时则返回0，如果出错则返回-1。
    注意：
  • 三个套接字集合分别关注三个不同的就绪状态，如果需要同时监控某个套接字sockfd的不同就绪状态，则需要将此套接字放入相应的套接字集合中；当 select() 返回时，三个集合中未处于就绪状态的套接字将被自动清零，因此如果要重复监控它们，则需要重新设置这些套接字集合。
epoll

原理：epoll是Linux内核为处理大批量文件描述符而作了改进的poll，是Linux下多路复用IO接口select/poll的增强版本，它能显著提高程序在大量并发连接中只有少量活跃的情况下的系统CPU利用率。另一点原因是因为epoll并没有像select/poll一样随着文件描述符数量的增加把用户空间与内核空间的数据拷贝次数成比例增加，而是固定了一些数量。

epoll的两种工作方式：LT（水平触发）和ET（边缘触发）
LT模式：当epoll_wait检测到描述符事件发生并将此事件通知应用程序，应用程序可以不立即处理该事件。下次调用epoll_wait时，会再次响应应用程序并通知此事件。
ET模式：当epoll_wait检测到描述符事件发生并将此事件通知应用程序，应用程序必须立即处理该事件。如果不处理，下次调用epoll_wait时，不会再次响应应用程序并通知此事件。

创建epoll对象：
#include <sys/epoll.h>
int epoll_create(int size); //size必须大于0
返回值：成功返回一个epoll文件描述符，失败返回-1
添加和删除事件
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
参数：
epfd：epoll_create函数返回的epoll文件描述符
op：对文件描述符的操作类型
EPOLL_CTL_ADD：注册新的fd到epfd中
EPOLL_CTL_MOD：修改已经注册的fd的监听事件
EPOLL_CTL_DEL：从epfd中删除一个fd
fd：需要监听的文件描述符
event：告诉内核需要监听的事件
监听事件
int epoll_wait(int epfd, struct epoll_event *events,int maxevents, int timeout);
参数：
epfd：epoll_create函数返回的epoll文件描述符
events：用于回传epoll_wait函数监听事件的数组
maxevents：告诉内核events数组中包含多少个元素
timeout：超时时间
返回值：成功返回有多少文件描述符就绪，时间到返回0，出错返回-1

常见应用层协议

HTTP协议

HTTP的特点

  • 简单快速
    客户端向服务器请求服务时，只需传送请求方法和路径。请求方法常用的有 GET、PUT、POST、HEAD 等，每种方法规定了客户端与服务器通信的类型。由于HTTP协议非常简单，因此 HTTP 服务器的程序规模小，通信效率高。

  • 灵活
    HTTP 允许传输任意类型的数据对象。

  • 无连接
    HTTP 每次连接只处理一个请求，服务器处理完客户的请求并收到客户应答之后，即断开连接。这么做是为了节约服务器套接字文件资源。
    一个连接是由传输层来控制的，这不属于HTTP的范围。HTTP并不需要其底层的传输层协议是面向连接的，只需要它是可靠的，或不丢失消息的（至少返回错误），因此一般而言，HTTP 底层使用面向连接的TCP进行消息传递，但要注意连接并不是必须的，基于TCP也不是必须的。

  • 无状态
    HTTP 协议是无状态的，即 HTTP 自身不对请求和相应之间的通信状态进行保存，任何两次请求之间不存在依赖关系，换句话说就是每个请求都是独立的。

请求报文

  • 请求行
    • 请求方法
      • GET
      • POST
      • PUT
      • DELETE
    • URL
    • HTTP版本
  • 请求头
    • Host:用于指明服务器的主机名称。
    • User-Agent:用于指明发出请求的客户端类型。
    • Accept:用于告诉服务器客户端可以处理的内容类型。
    • Accept-Language:用于告诉服务器客户端可以处理的语言类型。
    • Accept-Encoding:用于告诉服务器客户端可以处理的内容编码。
    • Connection:用于告诉服务器客户端是否支持长连接。
    • Referer:用于告诉服务器请求的来源。
    • Authorization:用于告诉服务器客户端的认证信息。
    • If-Modified-Since：通过前一次响应Last-Modified的时间值，当条件不成立，请求成功返回。
    • Cookie：客户端告诉服务器Cookie属性。HTTP是无状态协议，客户端的多次请求能保持连贯，是因为有Cookie属性的帮助。
  • 请求体

典型HTTP请求报文头部
char *http_request = “GET /repo/boa-0.100.9.tgz HTTP/1.1\r\n”
“Range:bytes=0-\r\n”
“Host:www.boa.org\r\n\r\n“;

响应报文

  • 状态行
    • HTTP版本
    • 状态码
    • 状态描述
  • 响应头
    • Content-Length: 给出响应包体的大小，客户端可据此做读取准备，也可通过Head请求来获知。
    • Transfer-Encoding: 给出响应包体的编码形式，若出现该字段且其值为 chunked，则代表服务端将以分段方式返回资源数据。
    • Accept-Ranges: 表明支持部分Get请求，客户端通过Head请求获取该值，然后发送Range报头请求，获取资源部分表示。
    • Content-Encoding: 对应Accept-Encoding请求报头。
    • Content-Language: 给出响应包体采用的自然语言，对应Accept-Language请求报头，可能多个值。
    • Content-Location: 把请求资源的规范URI告知客户端，但并不要求其使用新URI。
    • Content-MD5: 实体主体MD5,可检测错误损坏。
    • Last-Modified: 资源表示的最后修改时间。
    • ETag: 比Last-Modified更精确，能反映1秒内变化。
    • Expires: 客户端可在一段时间内缓存整个响应（不光是实体主体），但服务器不保证该时间段内一定不更新。
    • Location: 与3xx系列响应密切相关，可表示新资源创建后的URI，也可表示默认URI，还可是补充建议URI。
    • WWW-Authorization: 配合401 Unauthorized响应代码，可指定认证方式WSSE等。
